> 우리 가족의 돈과 일상을 담는 지갑

| 항목 | 내용 |
|---|---|
| 서비스명 | 도깨비 지갑 |
| 영문명 | DOKKAEBI WALLET |
| 플랫폼 | iOS 네이티브 앱 (iPhone 우선, iPad 레이아웃 대응은 확장 과제) |

## 1. 배경과 목표

### 1.1 해결할 문제
- 가족의 돈 관리가 개인 가계부 앱, 메신저 단톡방, 종이 메모로 흩어져 있다.
- 공동 생활비와 개인 용돈이 섞여 누가 무엇에 얼마를 썼는지 알기 어렵다.
- 멤버십 카드와 쿠폰 바코드가 구성원마다 따로 있어 함께 쓰기 불편하다.
- 일정, 공지, 할 일이 메신저 대화에 묻혀 사라진다.

### 1.2 제품 목표
1. **가족 단위 통합**: 가계부, 지갑, 캘린더, 공지, 할 일을 하나의 가족 그룹 공간에서 관리한다.
2. **사생활 보호**: 함께 쓰되, 개인 전용 데이터는 서버(RLS) 수준에서 다른 사람에게 보이지 않는다.
3. **실시간성**: 한 구성원이 바꾼 내용(거래, 카테고리, 공지 등)이 다른 구성원 화면에 즉시 반영된다.
4. **오프라인 신뢰성**: 매장 계산대처럼 네트워크가 불안정한 곳에서도 지갑 바코드를 열 수 있고, 거래는 오프라인에서 기록한 뒤 나중에 동기화된다.
5. **프리미엄 경험**: 따뜻한 아이보리와 딥그린을 기반으로 한 절제된 고급 iOS UI.

### 1.3 성공 지표 (출시 후 3개월)
| 지표 | 목표 |
|---|---|
| 가족 그룹당 활성 구성원 수 | 평균 2.5명 이상 |
| 주간 활성 사용자 / 월간 활성 사용자 | 45% 이상 |
| 그룹당 월 거래 등록 건수 | 40건 이상 |
| 크래시 없는 세션 비율 | 99.5% 이상 |
| 실시간 반영 지연 (p95) | 2초 이내 |
| 콜드 스타트 후 홈 표시 (캐시 기준) | 1초 이내 |

| C. 가족 통합 카테고리 | 그룹 단위 공통 카테고리, 기본 카테고리, 사용자 정의, 아이콘·색상·순서, 사용 중지·삭제, 즉시 공유 |
| D. 소비 통계 | 월별 수입·지출, 카테고리 비율, 구성원별, 공동·개인 비교, 전월 대비, 기간 검색, 개인 데이터 보호 |
| E. 디지털 지갑 | 바코드·QR 저장 및 전체 화면 표시, 개인·가족 공유 지갑, 브랜드·카드명·번호·메모, 즐겨찾기·검색, 바코드 유형, 이미지 등록·스캔, 오프라인 캐싱 |
| F. 가족 캘린더 | 월·주·일 보기, 일정 CRUD, 제목·날짜·시간·장소·설명, 가족·개인 일정, 참여자, 반복, 알림 |

### 2.2 명시적 제외
- 포인트 통합, 포인트 이전, 결제 기능 (요구사항에 따라 제외)
- 송금, 실제 계좌 이체 실행 (가계부의 "이체"는 기록일 뿐 실제 돈이 움직이지 않음)
- 비공식 스크래핑 방식의 금융 데이터 수집 (보안·약관·법적 위험)

### 2.3 구현 난이도가 높은 기능과 대안
| 기능 | 어려운 이유 | 대안 / 단계적 접근 |
|---|---|---|
| 금융 거래 자동 수집 | 국내 마이데이터는 본인신용정보관리업 허가가 필요하고, 금융결제원 오픈뱅킹은 사업자 이용기관 등록과 보안 심사가 필요하다. iOS는 문자(SMS)에 접근할 수 없어 카드 승인 문자 파싱이 불가능하다. Apple FinanceKit은 국내 금융기관을 지원하지 않는다(출시 시점에 다시 확인). | 1단계: CSV/엑셀 내보내기 파일 가져오기(MVP). 2단계: 허가받은 데이터 제공업체(마이데이터 사업자 또는 정식 제휴 API 중계사)와 계약하고 Edge Function 기반 `FinancialProvider` 추상화로 연동. 3단계: 사업 규모가 되면 직접 인허가 검토. 상세 내용은 REQUIREMENTS.md §J 참고. |
| 일부 바코드 유형 생성 (EAN-13, UPC-A, Code39 등) | Core Image는 QR, Code128, PDF417, Aztec 생성만 지원한다. | EAN/UPC/Code39/ITF 인코더는 앱 내부에서 직접 구현한다(규격이 공개되어 있고 구현량이 적음). 그래도 생성하기 어려운 유형은 원본 이미지를 저장해 표시한다. |
| 서버 기반 정시 알림 (일정·마감) | Supabase에는 기본 푸시 기능이 없다. | 일정·마감 알림은 기기 로컬 알림(UNUserNotificationCenter)으로 예약하고, 다른 구성원에게 보내는 이벤트 알림은 Edge Function과 APNs로 보낸다. 예산 초과 같은 서버 판단은 pg_cron으로 처리한다. |
| 오프라인 쓰기 충돌 | 여러 구성원이 동시에 같은 데이터를 수정할 수 있다. | 클라이언트에서 UUID를 생성하고, `version` 컬럼으로 낙관적 동시성 제어를 한다. 충돌하면 서버 버전을 우선 적용하고 사용자에게 알린다(APP_STRUCTURE.md §8). |
| 개인 데이터를 제외한 가족 통계 | 비공개 거래를 합계에 넣으면 금액이 노출될 수 있다. | 통계는 "조회자가 볼 수 있는 거래"만 집계한다(RLS 적용 RPC). 화면에 "내가 볼 수 있는 내역 기준"이라고 표시한다. |

## 3. 핵심 설계 결정 (문서 간 공통 기준)

모든 문서는 아래 결정을 따른다. 결정을 바꾸면 관련 문서를 모두 함께 수정한다.

| # | 결정 | 내용 |
|---|---|---|
| D1 | 데이터 소유 단위 | 모든 주요 데이터는 `family_group_id`로 분리한다. **예외**: 개인 지갑 카드(`wallet_cards.scope = 'personal'`)는 사용자 소유이며 그룹과 무관하다. 사용자가 여러 그룹에 참여해도 같은 멤버십 카드를 다시 등록하지 않게 하기 위해서다. |
| D2 | 공동·개인 지출과 공개 범위는 서로 다른 축이다 | `expense_scope`(shared/personal)는 "누구의 돈인가", `visibility`(family/private/selected)는 "누가 볼 수 있나"를 뜻한다. 공동 지출은 반드시 `visibility = family`여야 한다(DB 제약). |
| D3 | 등록자와 실사용자 | `created_by`(기록한 사람)와 `spent_by`(실제로 사용한 사람)를 분리한다. |
| D4 | 금액 | `bigint`로 원 단위 정수를 저장하고 부호는 쓰지 않는다(유형으로 구분). 확장에 대비해 `currency char(3) DEFAULT 'KRW'`를 둔다. |
| D5 | 날짜와 시간대 | 시각은 `timestamptz`로 저장한다. 거래 기준일은 `occurred_on date`이며 그룹 시간대(기본 Asia/Seoul)로 계산한다. 월 시작일은 그룹 설정(1~28일)을 따른다. |
| D6 | 예산 범위 | 가족 예산은 공동 지출만, 개인 예산은 본인의 개인 지출만 집계한다. 그래서 비공개 데이터와 예산이 충돌하지 않는다. |
| D7 | 통계 권한 | 통계 RPC는 `SECURITY INVOKER`로 실행되어 RLS가 그대로 적용된다. 조회자는 볼 수 없는 거래를 집계에서도 볼 수 없다. |
| D8 | 반복 규칙 | RFC 5545 RRULE의 부분집합(FREQ, INTERVAL, BYDAY, BYMONTHDAY, UNTIL, COUNT)을 쓴다. 반복 거래와 반복 할 일은 서버(pg_cron)가 실제 행을 만들고, 반복 일정은 클라이언트에서 전개하며 예외 테이블을 둔다. |
| D9 | 식별자 | 모든 PK는 `uuid`이며 클라이언트에서 생성할 수 있다. 오프라인 생성과 중복 전송 방지(멱등성)를 위해서다. |
| D10 | 삭제 정책 | 사용자 데이터는 소프트 삭제(`deleted_at`)를 한다. 30일 뒤 pg_cron으로 영구 삭제한다. 동기화 시 삭제를 전파하기 위해서다. |
| D11 | 상태 관리 | iOS 17 `@Observable` 매크로 기반 ViewModel, `NavigationStack`과 탭별 Router를 사용한다. |
| D12 | 카테고리 범위 | 카테고리는 가족 그룹 단위로만 존재하며 개인별 카테고리는 없다. |

## 6. 환경 구성

| 환경 | Supabase 프로젝트 | 용도 |
|---|---|---|
| local | Supabase CLI (`supabase start`) | 개발, 마이그레이션, RLS 테스트 (pgTAP) |
| dev | dokkaebi-dev | 통합 개발, TestFlight 내부 배포 |
| staging | dokkaebi-staging | QA, 외부 베타 |
| production | dokkaebi-prod | 실서비스 (리전: ap-northeast-2 서울) |

- 앱 빌드 구성: `Debug`, `Staging`, `Release`. 각 구성의 `.xcconfig`에 Supabase URL과 anon key를 넣는다. service_role 키는 앱에 절대 넣지 않는다.
- 마이그레이션은 `supabase/migrations`에서 버전으로 관리하고, CI에서 staging에 먼저 적용한 뒤 production에 적용한다.
